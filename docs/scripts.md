# サーバー上で動くスクリプト一覧

EC2 インスタンスの中で何が動いているかの一覧。
すべて `server/` にあり、S3 経由で `/opt/palworld/` へ配布される（AMI には焼かない）。

設計の背景は [DESIGN.md](../DESIGN.md)、時間軸での流れは [sequence.drawio](sequence.drawio) を参照。

---

## 全体像

| スクリプト | 種別 | 動き方 | 何をしているか |
| --- | --- | --- | --- |
| `install.sh` | 起動時 1 回 | user_data から `exec` | OS 準備・DNS 登録・ゲーム取得・セーブ復元・systemd 起動 |
| `pal-guardian.sh` | **常駐** | 5 秒（スポット回収）/ 15 秒（ASG 終了指示） | 終了の兆候を見張り、掴んだら緊急セーブへ入る |
| `pal-idle-watcher.sh` | **常駐** | 60 秒でポーリング | 接続人数を数え、15 分無人なら自動停止する |
| `pal-backup.sh` | 定期実行 | タイマーが 5 分ごとに起動 | セーブを検証して S3 へ退避する |
| `pal-status.sh` | 定期実行 | タイマーが 30 秒ごとに起動 | 状態を S3 へ発行し、排他ロックの心拍を打つ |
| `pal-restore.sh` | 起動時 1 回 | install.sh から呼ばれる | S3 からセーブを復元し、開くワールドを指定する |
| `pal-graceful-stop.sh` | 契機ごと 1 回 | guardian / idle から呼ばれる | 原因を判定し、セーブしてから終了処理を進める |
| `pal-notify.sh` | 都度 | 各スクリプトから呼ばれる | Discord の Webhook へ通知を送る |
| `rcon.py` | 都度 | 各スクリプトから呼ばれる | ゲーム本体にコマンドを送る（Save・ShowPlayers 等） |
| `lib/common.sh` | ライブラリ | 全スクリプトが `source` | 設定読み込み・RCON・ロック・通知の共通処理 |

**ポーリングしているのは 2 つだけ**（guardian と idle-watcher）。
他はタイマー起動か、必要なときに 1 回走って終わる。

guardian の間隔が 2 つあるのは、**見張っている対象が 2 つあり、それぞれ猶予が違う**ため。
スポット回収は猶予が約 2 分しかないので 5 秒ごとに急いで確認するが、
ASG の終了指示は 300 秒の猶予があるので 15 秒ごとで足りる（API を無駄に叩かない）。
詳細は下の [pal-guardian.sh](#pal-guardiansh-中断検知の心臓部) を参照。

## 常駐するもの（デーモン）

systemd の `Type=simple` + `Restart=on-failure` で常時動き、落ちたら自動再起動する。

### pal-guardian.sh ★中断検知の心臓部

「終了させられそうだ」という兆候を 2 系統で見張り、掴んだ瞬間にセーブへ入る。
**このシステムの存在意義そのもの**を担う。

| | 系統 1: スポット回収 | 系統 2: ASG の終了指示 |
| --- | --- | --- |
| 何が起きている | AWS がハードウェアを取り上げる | 台数調整（`/pal stop`・置換）による終了 |
| どこを見る | IMDS `spot/instance-action` | `describe-auto-scaling-instances` |
| 猶予 | 約 2 分 | 300 秒 |
| **確認間隔** | **5 秒** | **15 秒** |

間隔が違うのは猶予の差がそのまま理由。ループは短いほう（5 秒）に合わせ、
系統 2 は 3 周に 1 回だけ実行して 15 秒間隔を作っている。

停止処理の完了後も **ループを抜けない**。スポット検知で先にセーブを終えた場合、
あとから来る ASG の終了指示に対して「フックを解放する役」が必要なため。
解放しないと ASG が 300 秒待たされ、復帰がそのぶん遅れる。

### pal-idle-watcher.sh

消し忘れ防止。60 秒ごとに RCON `ShowPlayers` を叩き、
接続者ゼロが 15 分続いたら自分で停止する（`idle_shutdown_minutes` で変更可）。

- **起動から 10 分間は判定しない** — 誰も繋ぐ前に落ちるのを防ぐ猶予
- **RCON が応答しない時はカウンタをリセット** — 遊んでいる最中に落とすのが最悪なので、
  判断できないときは止めない側に倒す
- 停止時は自分で `SetDesiredCapacity(0)` を呼ぶ（他の停止パターンと逆向き）

## タイマーで定期実行されるもの

systemd の `.timer` が `.service`（`Type=oneshot`）を起動する。
実行が終わればプロセスは消えるので、常駐はしていない。

cron ではなく systemd timer を使っているのは、秒単位の間隔が扱えること、
ログが `journalctl` に統一されること、起動からの相対時間（`OnBootSec`）を
指定できること（このサーバーは起動時刻が毎回違う）の 3 点による。

### pal-backup.sh ─ 5 分ごと

セーブを S3 へ退避する。**多層防御の第 1 層**で、最悪でもロストを 5 分以内に抑える。

1. RCON `Save` でメモリ上のワールドをディスクへフラッシュ
2. `SaveGames` をローカルにスナップショットコピー
   （ゲームのオートセーブと tar が重なって不整合な断面を掴まないため）
3. 整合性チェック — `Level.sav` が 4KB 以上 / 前回比 50% 未満でない / tar が読める
4. tar + zstd を **単一オブジェクト**として PUT（＝原子的。途中で電源が落ちても既存は無傷）
5. 1 時間ごとに `archive/` へも複製（長期の世代管理）

検証に落ちたら `latest` は**触らず** `quarantine/` へ隔離する。
「バックアップが失敗した」より「良いバックアップを壊れたデータで上書きした」ほうが
致命的なので、疑わしい場合は必ず既存を温存する側に倒す。

`flock` で排他している。前回の実行が 5 分以内に終わらなかった場合に
2 つ目が並行起動するのを防ぐため。

### pal-status.sh ─ 30 秒ごと

2 つの役割を持つ。

- **`status.json` を S3 へ発行** — 接続人数・プレイヤー名・メモリ / CPU / ディスク・
  最終バックアップ時刻。Lambda がこれを読んで `/pal status` に答える
- **ロックのハートビート更新** — `lock/active.json` の時刻を更新し続ける。
  これが 90 秒途切れると、次のインスタンスが「前任者は死んだ」と判断して引き継ぐ

メモリと CPU をここで取っているのは、CloudWatch がハイパーバイザ側からしか
見えず OS 内部の情報を取得できないため。エージェント（カスタムメトリクス
月 $0.30/個）を入れる代わりに、既に動いているこのスクリプトで拾っている。

CPU 使用率は `/proc/stat` の累積値を前回実行時（30 秒前）と比較して算出する。
サンプリング用の `sleep` が不要で、30 秒平均になるぶんノイズも少ない。

## 契機ごとに 1 回だけ走るもの

### install.sh ─ インスタンス起動時

user_data から `exec` で呼ばれる構築処理の本体。約 250 行。

OS 準備（steamcmd・スワップ 4GB・palworld ユーザー）→ Route53 に自 IP を登録 →
ゲーム本体を用意（S3 キャッシュ優先、無ければ steamcmd）→ **セーブ復元** →
`PalWorldSettings.ini` を生成 → systemd ユニットを配置して起動 → 起動完了を通知。

**user_data 本体（`terraform/templates/user_data.sh.tftpl`）とは別物。**
あちらは設定を書き出して S3 からスクリプトを取ってくるだけの薄いラッパーで、
ロジックはすべてこちらにある。この分離のおかげで、スクリプトの修正は
`terraform apply` 不要（S3 を更新するだけ）で次回起動から反映される。

### pal-restore.sh ─ 起動時（install.sh から）

S3 からセーブを復元する。**多層防御の第 5 層**。

1. **ロックが消えるまで待つ** — 前任者の最終セーブが S3 に届く前に復元すると、
   古いデータを掴んで後で上書きしてしまう
2. `saves/latest.tar.zst` を取得 → 検証 → 展開
3. 検証 NG ならバージョン履歴を新しい順に、それも全滅なら `archive/` の最新へ
4. **復元後、`Level.sav` が最新のワールドを `DedicatedServerName` に書く**

4 が無いと、サーバーは復元済みワールドを無視して新規ワールドを作る
（＝プレイヤーには「キャラクリからやり直し」に見える）。この設定ファイルは
`SaveGames` の外にあるためバックアップ対象外で、実運用で踏んだ罠。

### pal-graceful-stop.sh ─ 停止時（guardian / idle-watcher から）

安全停止シーケンス。3 つの契機すべてがここに合流する。
`flock` とフラグファイルで**冪等**（何度呼ばれても 1 回だけ走る）。

引数で契機を受け取るが（`spot` / `lifecycle` / `idle` / `manual`）、
`lifecycle` は「ユーザー操作」「スポット起因の置換」「AWS 都合の置換」の
どれでも発生するため曖昧。そこで IMDS の痕跡と ASG の `desired` 値から
**原因を推理**して通知に明記する。

停止を言い出した Lambda と実行するサーバーが別マシンで、間を取り持つ AWS の
信号に理由を書く欄が無いことへの対処。`desired` は「誰が言い出したか」の
痕跡として必ず残るので、そこから復元している。

処理順序は [sequence.drawio](sequence.drawio) の停止シーケンス参照。
特に **ロック削除は必ずセーブのアップロード後**でなければならない。

## 呼ばれる側（ライブラリ・道具）

### lib/common.sh

全スクリプトが冒頭で `source` する共通ライブラリ。
`/etc/palworld/env`（user_data が生成）から設定を読み、以下を提供する。

- パス定数（`PAL_DIR` / `SAVE_DIR` / `WORK_DIR` / `STATE_DIR`）
- `imds_get` — IMDSv2 のトークン取得込みのメタデータ参照
- `rcon` / `rcon_broadcast` — RCON 実行（パスワードは tmpfs にキャッシュ）
- `lock_write` / `lock_release` / `lock_wait` / `lock_field` — S3 排他ロック
- `notify` — Discord 通知（失敗しても本処理を止めない）

### rcon.py

Source RCON プロトコルのクライアント。Python 標準ライブラリのみで約 80 行。

専用の CLI ツールが標準では入らないため自前実装した。Palworld の RCON 実装には
癖があり（応答パケットの終端が仕様どおりでない、`Broadcast` にスペースを含むと
以降が切れる）、それを吸収している。

接続先は `127.0.0.1:25575` 固定。**外部には一切開いていない**
（開けると管理コマンドをパスワード総当たりされる的になる）。

### pal-notify.sh

Discord の Webhook へ POST する。URL は SSM パラメータストアから復号して取得。

インスタンスから直接送っている理由は、「セーブが何バイトで整合性チェックを
通ったか」といった詳細は EC2 の中でしか分からないため。Lambda に伝えてから
送らせると中継の部品が 1 つ増える。

ただし**インスタンスがハングすると届かない**ので、AWS 側のイベントを拾って
Lambda から送る経路（EventBridge → Lambda）も併用している。無言で消えるのが
セーブ喪失の発見遅れに直結するため、あえて 2 系統にしてある。

## 動作確認したいとき

```bash
# ログを見る（SSM Session Manager でインスタンスに入ってから）
sudo journalctl -u palworld -f          # ゲームサーバー本体
sudo journalctl -u pal-guardian -f      # 中断監視
sudo journalctl -u pal-backup -n 50     # 直近のバックアップ結果
sudo journalctl -u pal-idle -f          # 無人検知

# タイマーの次回実行時刻
systemctl list-timers 'pal-*'

# 手動でバックアップを走らせる（/pal backup と同じ）
sudo /opt/palworld/bin/pal-backup.sh
```

スクリプトを修正したときは `terraform apply` で S3 が更新され、
**次回起動から**反映される。動いているサーバーに即時反映したい場合は
SSM 経由で `/opt/palworld/` へ sync し直す。
